## 4. Findings

### 1-未修复-中-正文六个月事实仍可能落入既有“无年度锚”序数回退，形成自然年式确认

- **位置**：plan §5.2“六个月事实须与现有邻近年度日历相符后确认财年和 Q2，不能默认所有六月结算都是自然年”；§6 实施后断言第 1 项。代码：`dayu/fins/pipelines/cn_report_selection.py:693-697`。
- **问题类型**：状态机漏洞 / 测试缺口 / 契约未闭环。
- **当前写法**：plan 正确要求六个月正文事实必须与邻近年度日历相符后才确认财年；但没有明确要求正文路径绕过既有“无 annual_ends 时按结束月份＋季度序数推年”的回退，断言清单也没有“无年度锚的六个月正文事实必须 unknown”这一负例。
- **反例/失败场景**：假设正文 owner 对某条六个月 results 来源得到 `end=2025-06-30`、`projection=Q2`，但同公司没有可用年度锚（年度 results 不在窗口、年度源不支持、或本地年度原件缺失）。若实现把 `end` 接入统一 resolver 后复用现有分支，`year is None and end is not None and projection is not None and not annual_ends` 会计算 `year = end.year + ((end.month + (4-2)*3 - 1)//12)`，返回 `(2025, Q2)`，即在没有任何年度日历证据时确认财年。我用当前代码、以同形标题验证过该分支返回 `(2025, Q2)`（仅用于触发既有代码路径，不作为产品输入）。
- **为什么有问题**：这正是用户明确要求不能发生的“自然年猜测”。四来源本轮恰好有 2024/2025 年末锚，所以立即验收不会暴露；但 plan 声称的通用 owner 支持范围包含无锚情形，且该错误会持久化为 fiscal_year/covered_fiscal_periods，并被 rebuild 继续沿用。
- **直接证据**：`cn_report_selection.py:693-697` 的回退只看 `annual_ends` 是否为空，不区分 `end` 来自标题还是正文；plan §5.2 的规则与 §6 断言清单没有覆盖“正文六个月 + 无 annual_ends”。
- **影响**：错误财年/覆盖区间写入 source/meta/manifest/processed；后续增量 skip 与 rebuild 会固化错误；与新正文输入的“唯一真源”目标冲突。
- **建议改法和验证点**：正文六个月事实必须要求 `relevant_annual_end_dates` 非空且 `fiscal_quarter_at` 返回非 None 才确认；显式禁止正文路径使用上述序数回退（或将回退严格限定为 title-path）。新增负例：正文六个月 + 无年度锚 → unknown；年度锚月份冲突（年结变更）→ unknown；非月末 → unknown。
- **修复风险**：低。
- **严重程度**：中。

### 2-未修复-中-正文 acquisition 的“仅补事实缺失”缺少 resolver-owned 的封闭判定，存在把冲突/歧义来源纳入正文准入的风险

- **位置**：plan §5.1/§5.2 的 acquisition 准入与“已识别的多主体、显式年份/日期冲突、区间简写歧义不能用正文覆盖”；§5.3“仅对上述有限 eligible 来源做 PDF 获取”。代码：`dayu/fins/pipelines/cn_report_selection.py:666-703,1077-1092`。
- **问题类型**：契约缺失 / 语义所有权边界。
- **当前写法**：plan 规定了正确的行为规则，但没有要求 resolver 暴露一个封闭的“仅缺年度/截止日事实”判定；只写了“具体类型/函数拆分由实现者决定”。
- **反例/失败场景**：当前 `resolve_hk_report_period` 对以下所有失败都返回同一个 `None`：主体不明、`has_unresolved_end_date`、4 位/2 位区间简写、分类家族歧义、分类/标题投影冲突、财年标签冲突、多个标题年份、缺年份。`_has_hk_unresolved_report_signal` 只判断“是否像财报”，不区分失败原因。若 downloader/eligibility 用 `facts is None and results family` 选择可获取来源，会把冲突/歧义来源也纳入正文获取；若后续扩展 resolver 时没有把既有 guard 全部放在正文事实消费之前，正文就可能“覆盖”一个本应保持 unknown 的冲突。
- **为什么有问题**：用户的核心要求是“未知与冲突不能被正文覆盖”。plan 的规则正确，但准入/确认的判定没有单一 owner 契约；实现者可能在各入口各写一套近似判断，形成第二真源。
- **直接证据**：`resolve_hk_report_period` 的多个 `return None` 分支没有原因码；`_has_hk_unresolved_report_signal` 只返回布尔值；plan 没有点名由哪个函数/结果类型承担“missing-facts-only”判定。
- **影响**：冲突来源被正文确认、unknown 被错误消除；或至少在 discovery 阶段对冲突来源做无谓的 PDF 获取，破坏“有限 eligible”承诺。两种结果都会削弱验收可解释性。
- **建议改法和验证点**：在 `cn_report_selection` 增加 resolver-owned 的封闭 missing-facts 判定/结果（例如返回 projection + 缺失事实类型，或在统一 resolution 结果中区分 `missing_year_or_end` 与其它失败原因）；downloader 只消费该判定做 acquisition。保留所有既有 guard 在正文事实之前。负例覆盖：多主体/9633 引用、unresolved end date、区间简写、分类家族歧义、财年标签冲突、多个标题年份；均必须继续 unknown。
- **修复风险**：低。
- **严重程度**：中。

### 3-未修复-中-prepared 资产的正文事实 SHA 绑定缺少明确的校验 owner，A 选期/B 落盘防护尚未在契约层闭环

- **位置**：plan §5.3“每个所选 source 只交接一次，同 candidate/URL/source/SHA/长度一致，commit 前核对实际原件与确认事实，避免选期用 A、保存 B”；§5.4。代码：`dayu/fins/pipelines/cn_download_models.py:380-402,457-471`、`dayu/fins/pipelines/cn_download_filing_workflow.py:185,276-284`。
- **问题类型**：契约缺失 / 安全边界。
- **当前写法**：plan 明确提出了 A/B 绑定不变量，但没有规定正文事实（含 `pdf_sha256`）如何进入 discovery result/candidate，也没有指定由谁在 prepared 资产交接时比较该 SHA。
- **反例/失败场景**：当前 `CnReportDiscoveryResult.__post_init__` 只按 provider/source_id 找 candidate，并调用 `require_matching_cn_annual_asset`；后者只比较 `asset.candidate == candidate`、字节长度和 asset 自身 SHA，不知道正文事实的 SHA。filing workflow 在 `prepared_asset is not None` 时直接使用该资产（`cn_download_filing_workflow.py:276-277`），且只有 `annual`（CN FY）才调用 `require_matching_cn_annual_asset`。如果 HK results 分支只在 `__post_init__` 检查 provider/identity/source，而没有把正文 owner 的 `pdf_sha256` 带进校验，那么同一 source key 下的不同 bytes（或未来重构丢失绑定）仍可能被 commit。
- **为什么有问题**：用户明确要求“原件 A 选期 B 落盘防护”。plan 的语义正确，但当前校验 owner 无法仅凭 candidate 元数据证明“选期所用 bytes = 落盘 bytes”；必须把正文事实 SHA 作为 typed 结果的一部分交给校验 owner。
- **直接证据**：`DownloadedReportAsset` 只有 candidate/bytes/SHA；`CnReportDiscoveryResult` 没有正文事实字段；`require_matching_cn_annual_asset` 不接收正文事实；filing workflow 的 HK prepared 路径不使用该函数。
- **影响**：选期与落盘可能来自不同字节；或者实现者把绑定检查放在 downloader 内部而 `__post_init__`/commit 边界没有校验，后续重构或测试夹具可绕过。数据完整性风险高于样式问题。
- **建议改法和验证点**：把正文事实（至少 source 身份、PDF SHA、页号/见证的 typed 结果）作为 discovery result/candidate 的显式输入，或在 `CnReportDiscoveryResult` 增加专门的 prepared 绑定校验；扩展后的 owner 必须要求 `asset.sha256 == body_fact.pdf_sha256`，并继续校验 URL/source/长度。为 prepared asset 与 local publication 两条路径都加同 source key、不同 bytes/SHA 的拒绝测试；CN FY 原校验保持不放宽。
- **修复风险**：低。
- **严重程度**：中。

## 5. Open Questions

1. **三页预算的支持范围是否在行为结果中写死**：§5 的行为结果写“对官方 results 家族……来源”，但真正的支持条件是“决定性本期声明在领先 1–3 个物理页内”。建议在行为结果/验收中明确：超出前三页才出现决定性声明的来源仍保留 unknown，避免实现者扩大为全文搜索或从比较列表头补日期。
2. **`report_date_source` 新值的确切字面量与 owner**：plan 要求“明确为正文来源”，但没有给新持久值的名称/允许值。该字段会进入 source/processed meta；建议在 plan 的实现交接中明确唯一字面量及 `hk_fiscal_calendar` 的投影函数，避免 downloader/upsert/rebuild 各自写值。
3. **`fiscal_year_source="source_document"` 对非十二月年结的中期是否足够**：四来源是十二月年结，日期年份等于财年；若通用支持范围包含六月年结，六个月截止日的财年可能由年度日历推出为下一年，此时 `source_document` 的语义会混合“正文日期”与“年度日历推导”。建议明确该值语义，或在本 slice 明确只支持“六月截止 + 邻近十二月年结”的已验证范围。
4. **`local_hk_annual_ends` 的 owner 边界**：plan 说它必须使用正文年度事实，但也说 workflow 读 snapshot、provider 不持仓储。建议明确它保持纯函数（接收已提取的正文事实/witness），而不是自行读仓储；否则 selection/pipeline 会获得存储访问。
5. **`period_resolution_version`/`period_resolution_sources` 是否随正文 resolution 更新**：当前 rebuild 写 `hk-period-v3` 和标题年度锚。正文来源应至少让版本/来源可重核，避免 rebuild 把正文事实误当成标题事实的历史版本。
6. **测试主命令的覆盖范围**：§6 的 11 文件命令没有列出直接受影响、且已存在断言 `local_hk_annual_ends`/selector 的 `tests/fins/test_f5_workflow_rebuild.py`、`tests/fins/test_f5_storage_calendar.py`。建议实施者把这两份及新增负例显式加入最终命令并记录实际结果。
